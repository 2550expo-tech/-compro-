ขั้นที่ 1: เขียนนิยามก่อนเขียนโค้ด

โจทย์ใน SRS มีแค่ "ประมาณวันที่ยอดเงินอาจต่ำ จากค่าเฉลี่ยรายจ่าย 7 วัน" และทีมได้ feedback ว่าคำว่า "ต่ำ" กำกวม ก่อนพิมพ์โค้ดสักบรรทัด ฉันจึงแปลงทุกคำที่กำกวมให้เป็นประโยคที่ ใส่ตัวเลขแล้วตอบได้ว่าถูกหรือผิด

ประโยคกำกวม (ทดสอบไม่ได้)ประโยคที่ฉันเขียน (ทดสอบได้)กลายเป็นเทสต์
"เตือนเมื่อเงินต่ำ"เงินต่ำ = ยอดคงเหลือ ≤ เส้นสำรอง ค่าเริ่มต้น ฿500ยอด ฿500 เส้น ฿500 → below_floor (TC-16)
"ค่าเฉลี่ย 7 วัน"รายจ่ายที่ยืนยันแล้ว ของวันนี้ + 6 วันก่อน ตามเวลาไทย ÷ จำนวนวันที่ใช้แอป (ไม่เกิน 7)TC-12, TC-13
"ประมาณวันที่"Runway = ปัดลง[(ยอด − เส้น) ÷ ค่าเฉลี่ย] · วันที่ = วันนี้ + RunwayTC-14
"ถ้าไม่มีข้อมูล"ค่าเฉลี่ย = 0 → no_spending ไม่แสดงวันที่ (ไม่หารด้วยศูนย์)TC-15
"สถานะ"< 7 วัน critical · < 14 วัน watch · ≥ 14 วัน healthyTC-17 (ลองที่ 6, 7, 14 พอดี)

นิยามชุดนี้อยู่ 2 ที่ และต้องตรงกันเสมอ: คอมเมนต์บนสุดของ src/domain/runway.ts:1-18 (สำหรับคนอ่านโค้ด) และหัวข้อ FR-6 ใน docs/TRACEABILITY.md:142-163 (สำหรับอาจารย์และคนในทีม ซึ่งมีตารางโยง "เงื่อนไขผ่าน → ฟังก์ชัน → เทสต์" ด้วย)

ลองถามตัวเองว่า "ถ้าให้เพื่อน 2 คนเขียนโค้ดจากนิยามนี้แยกกัน ผลจะออกมาเท่ากันไหม" ถ้าไม่แน่ใจ แปลว่ายังกำกวม เช่น "7 วัน" ต้องบอกด้วยว่านับวันนี้ไหม ใช้เวลาประเทศไหน และนับรายการแบบร่างไหม

ขั้นที่ 3: เขียนสูตรให้เทสต์ผ่าน (เขียว)

คลิกขวาที่โฟลเดอร์ src/domain → New File → mini-runway.ts แล้วพิมพ์:

// Money Runway ฉบับย่อ: เงินเป็นบาท และรับรายจ่ายรายวันมาเป็นลิสต์ export type Status = 'healthy' | 'watch' | 'critical' | 'below_floor' | 'no_spending'; /** ค่าเฉลี่ยรายจ่ายต่อวันจาก 7 วันล่าสุด (ถ้ามีไม่ถึง 7 วัน หารเท่าที่มี) */ export function average7(dailySpend: number[]): number { const last7 = dailySpend.slice(-7); if (last7.length === 0) return 0; const total = last7.reduce((sum, x) => sum + x, 0); return total / last7.length; } /** เงินพอใช้อีกกี่วัน และสถานะ */ export function runway(balance: number, floor: number, avg: number) { const spendable = balance - floor; if (spendable <= 0) return { days: 0, status: 'below_floor' as Status }; if (avg <= 0) return { days: null, status: 'no_spending' as Status }; const days = Math.floor(spendable / avg); const status: Status = days < 7 ? 'critical' : days < 14 ? 'watch' : 'healthy'; return { days, status }; }

ข้อมูลเข้าลิสต์รายจ่ายรายวันที่รวมมาแล้วรายการ Transaction ทั้งหมด ต้องกรองเองฐานข้อมูลเก็บเป็นรายการ ไม่ได้เก็บเป็นยอดรายวัน

เทสต์ผ่านยังไม่พอ ก่อนไปขั้นถัดไปฉันรัน 3 คำสั่งนี้เสมอ แต่ละตัวจับปัญหาคนละแบบ:

คำสั่งจับอะไรได้ตัวอย่างกับ FR-6
npm testตรรกะผิดเขียน <= แทน < (เพิ่งลองไป)

npx expo lintรูปแบบที่มักทำให้เกิดบั๊กรายการ dependency ของ useMemo ใน useMoney (ดูด้านล่าง)

ตัวอย่าง typecheck: ถ้าเขียนโค้ดคิด "พรุ่งนี้เหลือกี่วัน" แบบนี้

const r = computeRunway({ balanceSatang: 350000, floorSatang: 50000, averageSatang: 14500 }); export const tomorrow = r.days + 1; 
error TS18047: 'r.days' is possibly 'null'.

TypeScript เตือนว่า days อาจเป็น null (กรณีไม่มีรายจ่าย) ถ้าปล่อยไว้ ผู้ใช้ที่ยังไม่มีรายจ่ายจะเห็นคำว่า "null วัน" หรือ NaN บนจอ วิธีแก้คือเช็กก่อน เช่น r.days === null ? 'คำนวณไม่ได้' : r.days + 1 ซึ่งเป็นเหตุผลที่ในหน้าจอจริงมีฟังก์ชัน daysText คอยแยกกรณี (บรรทัด 22–26 ของ runway.tsx)

ตัวอย่าง lint ที่เกิดกับ FR-6 จริง: ใน useMoney ฉันใส่ today ไว้ในรายการ dependency ของ useMemo ทั้งที่ข้างในไม่ได้ใช้ตัวแปรนี้เลย ถ้าลบบรรทัดปิดคำเตือนออกแล้วรัน lint จะได้ (ลองแล้ว):

457:6  warning  React Hook useMemo has an unnecessary dependency: 'today'.
               Either exclude it or remove the dependency array  react-hooks/exhaustive-deps

lint คิดว่าใส่เกินมาโดยไม่ตั้งใจ แต่ฉันตั้งใจ: พอ today เปลี่ยนตอนเที่ยงคืน useMemo จะคิดยอดและ Runway ใหม่ หน้าต่าง 7 วันจึงเลื่อนเองแม้เปิดแอปค้างไว้ ฉันจึงปิดคำเตือนเฉพาะบรรทัดนั้น พร้อมเขียนคอมเมนต์บอกเหตุผลไว้บรรทัดก่อนหน้า (src/data/AppProvider.tsx:456-457) กฎคือ ปิดคำเตือนได้ ถ้าเขียนเหตุผลไว้ให้คนถัดไปอ่าน

ขั้นที่ 5: ต่อสูตรเข้ากับข้อมูลจริง

จากนั้นเปิดหน้า GitHub ของโปรเจกต์ จะมีปุ่ม Compare & pull request ให้เพื่อนในทีมช่วยอ่านโค้ด (code review) ก่อนรวมเข้า main

ในประวัติของโปรเจกต์ไม่มี merge commit เลย แปลว่าทีม push ขึ้น main ตรง ๆ ทุกครั้ง ซึ่งเร็ว แต่ไม่มีคนอ่านโค้ดก่อนรวม ทีมชดเชยด้วยเทสต์อัตโนมัติที่รันทุกครั้งที่ push ถ้าอาจารย์ถาม ให้ตอบตรง ๆ แบบนี้ และบอกว่าถ้าทีมใหญ่ขึ้น ควรใช้ branch + Pull Request ตามด้านบน

ทุกครั้งที่มีโค้ดใหม่บน main, GitHub Actions จะทำงานต่อให้เอง 4 งาน (ไฟล์อยู่ในโฟลเดอร์ .github/workflows):

ไฟล์ทำอะไรผลที่ได้
web.ymlbuild เว็บ → รัน unit test → รัน E2E บน Chromium → ถ้าผ่านทั้งหมดจึงเผยแพร่เว็บ MindPay บน GitHub Pages อัปเดต (ถ้าเทสต์ไม่ผ่าน เว็บจะ ไม่ ถูกเผยแพร่ และแนบภาพหน้าจอตอนพังไว้ให้ดู)
e2e-webkit.ymlรัน E2E ชุดเดียวกันบนเอนจินของ Safari แบบ iPhone โหมดมืดรู้ว่าผู้ใช้ iPhone ใช้ได้ด้วย (ไม่ขวางการเผยแพร่เว็บ)
android-apk.ymlbuild ไฟล์ติดตั้ง Android บนเซิร์ฟเวอร์ของ GitHub (15–25 นาที)ไฟล์ mind-pay.apk ในหน้า Releases
eas-update.ymlส่งโค้ด JavaScript ใหม่ไปให้แอปที่ติดตั้งแล้ว (EAS Update)แอปในมือถือโหลดเองเบื้องหลัง เปิดครั้งถัดไปได้เวอร์ชันใหม่ ไม่ต้องลง APK ใหม่

เพราะฉันเขียนแถบเลื่อนด้วย JavaScript ล้วน (src/ui/Slider.tsx) ไม่ได้ติดตั้งไลบรารีที่มีโค้ด native เพิ่ม EAS Update จึงส่งไปให้แอปที่ติดตั้งแล้วได้ทันที ถ้าใช้ไลบรารีแถบเลื่อนสำเร็จรูปที่มีโค้ด native ทุกคนต้องลง APK ใหม่ (ข้อความ commit ของงานนี้เขียนเหตุผลนี้ไว้เอง)
